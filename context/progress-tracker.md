Logged during the Step 3 review; deliberately not fixed there to keep the step a behavior freeze (no new reducer action, no new UI surface). Each is tagged with the step that owns it.

- **[Step 4] Caret/focus loss on pill remove & after insert (finding #3).** Index-based React keys (`` `${partIndex}:TEXT` ``) plus the narrow empty TEXT segment lose focus/caret when parts are removed/merged or after an insert. Step 4 consolidates the per-segment `<input>`s into one inline contenteditable token surface and owns caret/selection — do not patch the per-segment inputs first.
- **[Step 4] Duplicate `aria-label`s on multi-TEXT cells.** A value with >1 TEXT segment ("Up to `[pill]` hours") gives both `<input>`s the same `aria-label` ("Value text for <row>"), so SR users can't tell the leading segment from the trailing one. Resolve in the Step 4 rewrite rather than over-polishing a surface that is about to be replaced.
- **[Step 4] Empty TEXT segment is fiddly to click (carried from Step 2).** ~2ch min-width; consider auto-focusing the trailing TEXT right after `INSERT_VALUE_PART`. Part of Step 4's caret work.
- **[Step 6] `normalizeRows` does no per-row validation (finding #4).** It casts `value as EditorRow[]` for any array. No live risk today (no Save path writes `rows`; loaded templates carry `[]`), but malformed persisted rows would render garbage / crash once Save lands. Add a safe per-row parse (narrow `unknown` → typed row) at the load/save boundary, and re-validate server-side.
- **[Step 6] Finalize provisional row keys at Save (finding #1 follow-through).** Derive `slugifyKey(label)` for rows still carrying a provisional `row_N`/`section_N` key, enforce uniqueness within the template, and never re-derive a finalized key. Watch the case where a merchant-typed label legitimately slugs to `row`/`section` — track "was this key ever finalized?" rather than matching the string alone. Bundle with the server-side 200-row + `shopId` re-check.
- **[Later, low priority] `insertActive` optimism at the cap.** `insertActive` sets `scrollTargetRef`/`activeRowId` before the reducer runs; at the cap the reducer no-ops (returns the same array), so `activeRowId` could point at a never-added row and the scroll ref stays stale. Unreachable today (all row-creating buttons are `disabled` at the cap), but if a later step adds a keyboard shortcut / programmatic add that bypasses the disabled button, guard `insertActive` on `!atCap` or only set active/scroll when `rows.length` actually grows.

Full strategy doc kept at `~/.claude/plans/there-is-no-automated-encapsulated-yeti.md`. - **Editor View Toggle Decision (Session 2026-06-14):** The view toggle is now a **single view state** with four mutually-exclusive segments — **Edit** (pencil + label), a divider, then **Desktop / Tablet / Mobile**. This **supersedes** the 2026-06-11 "stays fully editable in every viewport" decision: only **Edit** is editable; Desktop / Tablet / Mobile are **read-only previews** of how the table renders for shoppers at that width (mobile = stacked label-over-value). Rationale + scope:
  - **Device views are view-only (`.preview`):** all editor chrome is hidden (toolbar, hint, gutter, add-row button, edit box, field picker), the gutter column collapses, and edit highlights / interactions are stripped. The table renders exactly like the storefront. This is a deliberate change to the editor's interaction flow — editing happens **only** in the Edit view, then the merchant switches to a device segment to inspect the storefront result. No separate preview panel (the WYSIWYG-rendering principle is unchanged; what changed is that previews are now read-only and live behind the device segments instead of every viewport being editable).
  - **Preview stand-in values:** read-only device views show resolved placeholder values for dynamic parts (e.g., a stand-in for the Battery Life row) so the preview reads like a real storefront table.
  - Validated in the mockup ([design/spec-editor-mockup.html](design/spec-editor-mockup.html)); the production editor's Desktop/Tablet/Mobile rendering still belongs to the later styling/persistence slice (it was never a numbered editor step), but it must now be built as **read-only**, not editable.

- **Multiline / `LINE_BREAK` decision (Session 2026-06-15):** Studied real merchant spec tables (Startech, Amazon, Walmart, eBay, Best Buy). Confirmed values need **hard-break lines** (author-intended, e.g. a "Features" list, one item per line) on top of automatic soft-wrap, but **no** inline rich formatting, links, or widgets for MVP (links = the roadmap's Phase 4 URL field; star-rating widgets out). Decisions locked:
  - **New `LINE_BREAK` value part** added to `data-model.md` §7 (additive; product-agnostic; ignored by the comparison-readiness invariant and the 200-row cap; renders as a hard break in editor + storefront). Soft-wrap stays free (CSS). This is the **only genuine net-new scope** vs. the committed PRD/roadmap — everything richer (zebra striping, separate header styling, accordion, style presets, links) was already phased on `feature-roadmap.md` as Phase 2/4, so deferring them follows the existing plan rather than cutting scope.
  - **`hideWhenEmpty` is whole-row, never per line** (`data-model.md` §10): a row hides only when its entire resolved value is empty (all dynamic parts empty across all lines); `LINE_BREAK` carries no content. The existing "hide when dynamic parts empty" rule is unchanged — just clarified as whole-row, with no per-line hide logic.
  - **Editor:** hard-break multiline becomes **sub-step 4.4** of the inline-pill step (same `contenteditable` surface), not a standalone step. It **supersedes** the Step 4 doc's "value shape unchanged / no new part type / no new reducer action" absolutes (now scoped to 4.1–4.3). 4.4 may add one caret-aware insert/split action (`INSERT_VALUE_PART` only appends, so it can't express a mid-caret split); deletion reuses `REMOVE_VALUE_PART` + `normalizeValueParts`. The `LINE_BREAK` member of the `ValuePart` union in `app/utils/rows.ts` is added in 4.4, not now. A full editor framework (Lexical) was considered and **rejected** — no committed MVP feature justifies it (paste is row-level bulk-create, not inline-rich; no inline formatting anywhere). See the 2026-06-15 amendment in `context/features/05-editor-step4-inline-pills.md`.

- **Smart-pill creation model — pick-then-insert (Session 2026-06-15):** Reversed the earlier insert-then-fill / placeholder-pill design. A pill is now **created complete**: an **Insert field** toolbar button (disabled when there is no active caret) opens a focus-trapped **modal**; the merchant picks a native field / metafield (Steps 6–9 content) and clicks **Insert** → a complete `SHOPIFY_FIELD`/`METAFIELD` pill drops at the **saved caret**; **Cancel** / Esc / outside-click inserts nothing. Rationale + consequences:
  - **Lower dev risk:** the picker lives entirely **outside** the `contenteditable`, so it never entangles the caret model (the editor's hardest problem). The only new editor duty is to **save the caret `Range` before the modal opens and restore it on Insert**.
  - **Container = modal, not popover** (decided after weighing both): room for the growing search + native-fields + live-metafields content and **zero positioning math** inside the embedded admin iframe (popover anchoring is fiddly there — see [[polaris-web-component-gotchas]]). Popover is a possible later polish, not now.
  - **No active caret → Insert field is disabled** (locked).
  - **Retires the placeholder pill:** `placeholderMetafieldPart()` and the `Metafield · choose field` state are gone — pills are only ever rendered complete, so Step 4 has no empty-pill state to style/guard and no incomplete reference can reach the storefront. The `Metafield · <key>` / `Field · <field>` labels + icons stand. **`data-model.md` needs no change** (METAFIELD already requires namespace + key — the model is now strictly honored, with no transient empty-key state).
  - **Shared reducer action:** insertion uses the **same caret-aware insert/split** action that 4.4's `LINE_BREAK` needs — one action serves both pill insert and line break.
  - **Step 5 redefined** from "popover anchored to a placeholder pill" to "the **Insert field** modal shell + caret save/restore + caret-aware insert"; Steps 6–9 are unchanged in substance (they populate the modal). See the pick-then-insert amendment in `context/features/05-editor-step4-inline-pills.md`.
  - **Editing an existing pill (confirmed 2026-06-15):** click a pill → reopen the modal **pre-filled** → **Update** replaces the field (Cancel leaves it untouched). One modal serves both create (**Insert**) and edit (**Update**).
