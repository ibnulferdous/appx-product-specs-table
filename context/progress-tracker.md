- **Editor Step 4 build notes (Session 2026-06-16):** Built and browser-verified the contenteditable value surface (see the "Editor Step 4 complete" entry under Completed). Two in-browser findings forced deviations from the Step 4 doc's assumptions, plus one piece of verification scaffolding:
  - **Polaris `s-*` color tokens are NOT exposed to light-DOM CSS (confirmed in-browser).** `--p-color-*` / `--s-color-*` all resolve empty on `document.documentElement`, `body`, and even on `s-*` hosts — they live inside each component's shadow DOM. So the Step 4 doc's plan to style the token via `var(--p-color-text-link)` does not work in this build. **Resolution:** `useCapturedTokenColor()` reads Polaris's own link color once from a throwaway `<s-link>`'s (open) shadow root — measured `rgb(0, 91, 211)` — and publishes it as `--appx-token-color` on the document; the scoped CSS uses that var for the token text and mixes the hover/caret-on tints from it via `color-mix`. This keeps the blue a genuine Polaris value with **no hardcoded hex**, degrading to `currentColor` if the read fails. (New gotcha worth a memory — see [[polaris-web-component-gotchas]].)
  - **Contenteditable trailing-empty-line caret (the two-`<br>` trick).** A single trailing `<br>` does not create an addressable empty line — the browser snaps the caret before it, so pressing Enter at end-of-content and typing put the new text on the *previous* line. - **Editor Step 5 build notes (Session 2026-06-16):** Built and browser-verified the "Insert field" modal + caret bridge (see the "Editor Step 5 complete" entry under Completed). The Step 5 doc's two open questions are resolved, with one deliberate design deviation worth recording:
  - **`<s-modal>` works in this CDN build — control it with the App Bridge Modal API.** The doc flagged a build-risk (this build has a history of web components not matching docs). In-browser, `<s-modal>` opens/closes reliably via `shopify.modal.show(id)` / `shopify.modal.hide(id)` (from `useAppBridge()`), renders the `primary-action` / `secondary-actions` slotted buttons, and provides the focus trap, Esc, and outside-click dismiss **natively**. The declarative `commandFor`/`command` path was **not** needed and is not used. No hand-built focus trap, no positioning math — the reason a modal beat a popover.
  - **Saved-selection model (deviation from the doc's literal gate).** The doc proposed "value-cell blur nulls the live caret + disables the button," guarded against the click-swallow race by `preventDefault()` on the button's `pointerdown`. In practice that is fragile on an `<s-button>` web component **and** breaks keyboard use (you must move focus off the cell to reach the button). **Resolution:** a value-cell blur does **not** clear `activeCaretRef` or disable the button; the gate is dropped only when a **Label / Section field gains focus** (`onFocus` → `onCaretChange(rowId, null)`), and `onDelete` clears it if the saved row is removed. This is the standard rich-text-toolbar "saved selection" pattern: the toolbar operates on the last value-cell caret even though focus has moved to the button/modal. It eliminates the disabled-flip-swallows-the-click race **and** keeps the button keyboard-reachable. Consequence: a pure blur to empty space leaves the button enabled with a saved caret (intended) — the gate tracks "are you editing a value," not "is a value cell literally focused right now."
  - **One caret-restore path, reused.** An external (modal) insert restores the caret through the **same** `ValueCell` reconcile-effect mechanism as an internal edit — the container queues `saved.linear + 1` in a ref-held `pendingCaretByRowRef` Map (stable identity, memoization-safe), and the effect focuses the host + `setCaretLinear` when it sees an entry for its row. No second caret system.
  - **Step 5 stub pill (`STEP5_STUB_PILL`).** Insert drops a fixed, *complete* `SHOPIFY_FIELD` `vendor` pill — honoring the always-complete invariant (never the retired keyless placeholder) — purely to prove the wiring. **Step 6 replaces it** with the field the merchant picks and turns Insert into disabled-until-a-field-is-selected.

- **Editor Step 7 build notes (Session 2026-06-17):** Built and browser-verified the modal search box (see the "Editor Step 7 complete" entry under Completed). The Step 7 doc's three open questions are resolved, with one in-browser deviation worth recording:
  - **Auto-focusing the search field must be DEFERRED past the modal's open animation (new gotcha).** App Bridge's `<s-modal>` plays a **view transition** when it shows. The first implementation focused the search field via a double-`requestAnimationFrame` (~32 ms after `shopify.modal.show`), i.e. **mid-transition** — this aborted the view transition and surfaced **`InvalidStateError: Transition was aborted because of invalid state`** in the **admin's** console (logged on the top admin page, not our bundle), and once correlated with a modal that wouldn't close on Insert. Step 6 had *no* console errors, so the regression was clearly the new focus call. **Resolution:** focus the field with a `setTimeout(…, 350)` so it lands **after** the open animation. Verified in-browser that this both (a) focuses the search box on open (the merchant can type immediately — typing "weight" with no prior click filtered the list) **and** (b) produces **no** `InvalidStateError` across repeated open/close/insert/edit cycles. (Removing auto-focus entirely also cleared the error but left native focus on the modal's ✕ close button, so the merchant had to click/Tab to the search box first — the deferred focus keeps the type-immediately UX without the error.) This answers the doc's "Auto-focus inside `<s-modal>`" open question: immediate focus fights the transition; deferred focus does not. Worth a memory — see [[polaris-web-component-gotchas]].
  - **`<s-search-field>` works in this CDN build** (another positive vs the [[polaris-web-component-gotchas]] track record): labelled (`labelAccessibilityVisibility="exclusive"` hides it visually, keeps it for SR), controllable via `value`, and `onInput` fires per keystroke (before `onChange`) with the text on `event.currentTarget.value`. It also renders a native clear (✕) affordance. No fallback to a plain `<input type="search">` was needed.
  - **`<s-choice-list>` survives its `<s-choice>` children being filtered** — the controlled `values={[selectedField]}` keeps reflecting/committing the selection even when that value is **not currently rendered** (the keep-selection round-trip: select → filter out → still selected → commit works). This validated the doc's locked "search is find-only, never deselects" decision in the actual build.
  - **Selection vs. filtering is independent** (locked decision, confirmed live): `searchQuery` and `selectedField` never touch each other; the committed pill is whatever `selectedField` holds regardless of what is visible. Reset hygiene holds — `searchQuery`/`selectedField`/`editTarget` all reset on every open and on Cancel, so create/edit opens carry no stale query, pick, or target.
